```
  enforce     branch/guard/rejection enforces a requirement

  interop     behavior is shaped by observed compatibility
```

**Assistant:**

I'd define it in SpecTrace, but narrowly.

Not as "every repo must use `// spectrace:...` comments," and not as a C#-specific mandate. I'd define a **source provenance model/profile** in the SpecTrace requirements, then make the exact comment/attribute style a **reference convention**.

That avoids both problems:

- It does not pollute the core standard with one language's syntax.
- It does not leave adopters with totally incompatible styles.

The split I'd use:

**Canonical SpecTrace Requirement:**
Define that source provenance anchors are optional, non-authoritative evidence-discovery inputs.

Normative rules could say:

```
If a repository claims source provenance support:
- source anchors MUST reference valid REQ-... identifiers;
- source anchors MUST be treated as non-canonical implementation evidence;
- tooling MUST emit generated evidence snapshots, usually `code_ref` or `source_coverage`;
- source anchors MUST NOT imply verification success;
- the repository MUST document its accepted source anchor syntax;
- the repository SHOULD keep human-facing anchor text short and local to the code decision.
```

**Reference Recommendation:**
Then publish the C# convention as the blessed/default style:

```csharp
// spectrace:enforce REQ-... - short local reason.
```

and:

```csharp
[SpecTrace("REQ-...", Relation = "derive")]
```

I would probably define relation tokens as a **recommended vocabulary**, not hard core semantics at first:

```
derive
enforce
interpret
interop
temporary
```

The key is that the standard can say: "If you use relation metadata, use this vocabulary unless your repository documents an extension." That prevents wild-west drift without pretending every language should annotate code the same way.

So my answer is: **yes, put the governing rules in the SpecTrace requirement set; keep the exact syntax as a reference convention.**

For `Http3Server.cs`, I'd use **rationale anchors**, with SpecTrace requirement anchors as one subtype. The file has at least five different "why" categories:

- `spec`: HTTP/3/QPACK rules, stream types, SETTINGS, HEADERS/DATA sequencing.

I would not document all of that with only `spectrace:begin`. I'd use a more general structured comment grammar:

```csharp
// rationale:begin <anchor-id> kind=<kind> refs=<refs> - <short why>
...
// rationale:end <anchor-id>
```

Example for constants:

```csharp
// rationale:begin h3-response-buffering kind=perf refs=docs/analysis/incursa-h3-performance-diagnostic-review.md - response frames are chunked to bound write size and avoid per-byte writes.

// rationale:end h3-response-buffering
```

Example for SpecTrace-backed protocol behavior:

```csharp
// rationale:begin h3-required-uni-streams kind=spec refs=REQ-QUIC-RFC9114-S6-0001,ARC-QUIC-RFC9114-0002 - server opens control and QPACK streams before request processing.
private async ValueTask<QuicStream> OpenRequiredUnidirectionalStreamsAsync(...)
```

Example for a local lifecycle decision:

```csharp
// rationale:begin h3-expected-shutdown kind=lifecycle refs=ARC-QUIC-RFC9114-0002 - cancellation, disposal, and QUIC shutdown are normal server-loop exits and are not errors.
```
